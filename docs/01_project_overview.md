## 2. Краткое описание проекта

**Finance Telegram Bot** — это персональный финансовый помощник внутри Telegram.

Пользователь не устанавливает отдельное мобильное приложение, не заполняет сложные формы и не открывает таблицы. Он просто пишет боту короткое сообщение обычным текстом:

```text
35 обед
```

Бот должен понять сообщение, определить сумму, тип операции, категорию, дату и сохранить запись как финансовую транзакцию.

Пример ответа:

```text
✅ Расход сохранён

Сумма: 35 TJS
Категория: Еда
Комментарий: обед

Остаток сегодня: 155 TJS
```

Ключевая идея продукта — **минимальное усилие для записи расходов**.

Пользователь должен иметь возможность записать расход за 3–5 секунд, без открытия отдельного интерфейса и без ручного выбора множества параметров.

## 3. Проблема, которую решает продукт

Многие пользователи хотят контролировать личные финансы, но быстро перестают вести учёт. Основные причины:

1. **Слишком много действий**

   * открыть приложение;
   * выбрать счёт;
   * выбрать категорию;
   * ввести сумму;
   * указать дату;
   * сохранить.

2. **Нет привычки**
   Пользователь не хочет каждый день заходить в финансовое приложение. Telegram уже открыт постоянно, поэтому бот снижает барьер входа.

3. **Сложные интерфейсы**
   Многие финансовые приложения перегружены графиками, счетами, инвестициями, банковскими интеграциями и настройками.

4. **Нет мгновенной обратной связи**
   Пользователь записывает расход, но не понимает сразу, как это влияет на его день, неделю или месяц.

5. **Учёт начинается сложно**
   Пользователь часто думает: “Мне нужно сначала всё настроить”. В этом проекте пользователь может начать с первой записи сразу после `/start`.

Finance Telegram Bot решает эти проблемы за счёт простого текстового ввода и коротких полезных ответов.

## 4. Цели проекта

### 4.1 Главная цель

Создать Telegram-бота, который позволяет быстро вести личный финансовый учёт через обычные текстовые сообщения.

### 4.2 Цели MVP

MVP должен позволять пользователю:

* пройти простой онбординг;
* записывать расходы свободным текстом;
* записывать доходы свободным текстом;
* получать автоматическую категорию операции;
* видеть остаток дня после каждой записи;
* смотреть отчёты за день, неделю и месяц;
* смотреть историю последних операций;
* удалять последнюю операцию;
* экспортировать данные в CSV;
* получать ежедневное напоминание.

### 4.3 Продуктовые цели

Продукт должен быть:

* быстрым;
* понятным;
* привычным;
* надёжным;
* не перегруженным функциями;
* полезным даже без dashboard;
* пригодным для расширения в сторону бюджетов, долгов, графиков и AI-категоризации.

### 4.4 Технические цели

Техническая реализация должна:

* работать на Cloudflare Workers;
* использовать Telegram webhook;
* хранить данные в Cloudflare D1;
* использовать Drizzle ORM для типизированной работы с базой;
* использовать Cloudflare KV для временных состояний и идемпотентности;
* быть написана на TypeScript;
* иметь модульную структуру;
* иметь unit-тесты для парсера и отчётов;
* не хранить секреты в коде;
* изолировать данные каждого пользователя через `user_id`.

## 5. Целевая аудитория

### 5.1 Основная аудитория MVP

Основная аудитория первой версии — один пользователь или небольшая группа первых пользователей, которым нужно понять, куда уходят деньги каждый месяц.

Типичный пользователь MVP:

* хочет учитывать личные расходы;
* не хочет вести Excel вручную;
* не хочет устанавливать отдельное приложение;
* уже активно использует Telegram;
* хочет быстро записывать расходы;
* хочет видеть простые отчёты;
* не требует банковских интеграций на старте.

### 5.2 Расширенная аудитория будущих версий

После MVP продукт может быть полезен следующим группам:

#### Студенты

Потребности:

* контроль ежедневных расходов;
* лимит на день или неделю;
* простые категории: еда, транспорт, связь, учёба.

#### Фрилансеры

Потребности:

* учёт доходов по проектам;
* учёт рабочих расходов;
* экспорт данных;
* отчёты по месяцам.

#### Семьи

Потребности:

* общий бюджет;
* несколько участников;
* категории семейных расходов;
* лимиты по категориям.

#### Небольшие команды

Потребности:

* учёт мелких офисных расходов;
* фиксация долгов;
* отчёты за период;
* экспорт для внутренней отчётности.

> 💡 Дополнено: в overview указаны основные и расширенные аудитории. Здесь они расширены до конкретных потребностей, чтобы продуктовую цель было легче переводить в требования и задачи разработки.

## 6. Ключевая ценность продукта

Главная ценность Finance Telegram Bot — **скорость записи и немедленный финансовый контекст**.

Пользователь пишет:

```text
25 такси
```

Бот отвечает:

```text
✅ Расход сохранён

25 TJS · Транспорт · такси
Остаток сегодня: 130 TJS
```

Это важнее, чем просто сохранить данные.

Бот должен не только фиксировать операцию, но и сразу показывать пользователю, как эта операция влияет на его бюджет или остаток.

### 6.1 Почему Telegram-бот

Telegram-бот выбран потому что:

* Telegram уже установлен у большинства пользователей целевой аудитории;
* пользователь не должен устанавливать отдельное приложение;
* бот можно использовать с телефона и компьютера;
* текстовый ввод быстрее формы;
* inline-кнопки позволяют уточнять данные без сложного UI;
* webhook-модель хорошо подходит для serverless backend.

### 6.2 Почему не отдельное приложение на MVP

Отдельное приложение требует:

* frontend-разработки;
* авторизации;
* дизайна экранов;
* публикации в магазинах приложений;
* поддержки разных устройств;
* большего времени разработки.

Для MVP это лишнее. Первая версия должна доказать, что пользователю удобно вести финансы через Telegram.

## 7. Основной пользовательский сценарий

### 7.1 Первый запуск

Пользователь открывает бота и нажимает `/start`.

Бот:

1. приветствует пользователя;
2. объясняет принцип работы;
3. предлагает выбрать валюту;
4. устанавливает часовой пояс;
5. предлагает записать первый расход.

Пример:

```text
Привет. Я помогу быстро вести расходы прямо в Telegram.

Пиши расходы обычным текстом:
35 обед
120 продукты
+300 зарплата

Для начала выбери валюту.
```

Inline-кнопки:

```text
[TJS] [USD] [RUB] [Другая]
```

### 7.2 Запись расхода

Пользователь пишет:

```text
35 обед
```

Бот:

1. извлекает сумму `35`;
2. определяет тип `expense`;
3. определяет категорию `food`;
4. сохраняет транзакцию;
5. отвечает подтверждением;
6. показывает остаток сегодня.

### 7.3 Запись дохода

Пользователь пишет:

```text
+300 зарплата
```

Бот:

1. определяет тип `income`;
2. извлекает сумму `300`;
3. определяет категорию `income`;
4. сохраняет транзакцию;
5. обновляет баланс дня;
6. отвечает пользователю.

### 7.4 Просмотр отчёта

Пользователь пишет:

```text
/month
```

Бот отвечает:

```text
📊 Июнь 2026

Доходы:   3 200 TJS
Расходы:  1 850 TJS
Остаток: +1 350 TJS

Еда:        720 TJS
Транспорт: 310 TJS
Подписки:  200 TJS
Прочее:    620 TJS
```

### 7.5 Удаление ошибки

Пользователь случайно записал неправильный расход.

Команда:

```text
/delete_last
```

Бот показывает последнюю операцию и просит подтверждение:

```text
Удалить последнюю запись?

35 TJS · Еда · обед
```

Inline-кнопки:

```text
[Да, удалить] [Отмена]
```

## 8. MVP: состав первой версии

MVP — минимальная версия, которая уже даёт пользователю реальную пользу.

MVP не должен содержать все возможные финансовые функции. Его задача — проверить главный сценарий: пользователь быстро пишет расходы в Telegram и получает полезный отчёт.

### 8.1 Функции MVP

| №  | Функция              | Описание                                          | Приоритет |
| -- | -------------------- | ------------------------------------------------- | --------- |
| 1  | `/start`             | Запуск бота и онбординг                           | Must      |
| 2  | Выбор валюты         | TJS по умолчанию, возможность выбрать другую      | Must      |
| 3  | Запись расхода       | Свободный текст: `35 обед`                        | Must      |
| 4  | Запись дохода        | Через `+` или ключевые слова                      | Must      |
| 5  | Автокатегоризация    | По системному словарю и пользовательским правилам | Must      |
| 6  | Остаток после записи | Показывается после каждой транзакции              | Must      |
| 7  | `/today`             | Отчёт за текущий день                             | Must      |
| 8  | `/week`              | Отчёт за неделю                                   | Must      |
| 9  | `/month`             | Отчёт за месяц                                    | Must      |
| 10 | `/history`           | Последние 10 операций                             | Must      |
| 11 | `/delete_last`       | Удаление последней операции с подтверждением      | Must      |
| 12 | `/export`            | Экспорт CSV                                       | Should    |
| 13 | `/settings`          | Настройки валюты, языка, напоминаний              | Should    |
| 14 | `/cancel`            | Сброс текущего состояния                          | Must      |
| 15 | Напоминание          | Ежедневный cron reminder                          | Should    |
| 16 | Rate limiting        | Защита от флуда                                   | Must      |
| 17 | Webhook secret       | Защита webhook endpoint                           | Must      |
| 18 | Идемпотентность      | Защита от повторной обработки update              | Must      |

### 8.2 Минимальный набор категорий

В MVP должны быть системные категории:

| Код             | Название    | Тип     | Примеры ключевых слов               |
| --------------- | ----------- | ------- | ----------------------------------- |
| `food`          | Еда         | expense | обед, ужин, кофе, продукты          |
| `transport`     | Транспорт   | expense | такси, автобус, бензин              |
| `home`          | Дом         | expense | аренда, коммунальные, интернет дома |
| `communication` | Связь       | expense | телефон, мобильный, симка           |
| `entertainment` | Развлечения | expense | кино, игры, концерт                 |
| `health`        | Здоровье    | expense | аптека, врач, лекарства             |
| `clothing`      | Одежда      | expense | обувь, куртка, футболка             |
| `education`     | Образование | expense | курс, книга, обучение               |
| `subscriptions` | Подписки    | expense | chatgpt, spotify, netflix           |
| `income`        | Доход       | income  | зарплата, проект, фриланс           |
| `other`         | Прочее      | expense | fallback-категория                  |

### 8.3 MVP-ограничения

В MVP допускаются следующие ограничения:

* только один пользовательский профиль на один Telegram account;
* одна основная валюта на пользователя;
* без банковских интеграций;
* без web-dashboard;
* без распознавания чеков;
* без Excel-экспорта;
* без семейного режима;
* без платных тарифов;
* без полноценной AI-категоризации;
* без сложной аналитики.

> 💡 Дополнено: ограничения MVP сформулированы явно, чтобы команда не расширяла первую версию до слишком большого продукта.

## 9. Что не входит в MVP

Следующие функции не входят в MVP и не должны блокировать релиз первой версии:

### 9.1 Web-dashboard

Dashboard будет добавлен в версии 2.0.

В MVP все взаимодействие идёт через Telegram.

### 9.2 Графики

Pie chart, bar chart и line chart не нужны в MVP. Вместо них используются текстовые отчёты.

### 9.3 Распознавание чеков

Фото чеков, OCR и AI-анализ чеков относятся к версии 3.0.

### 9.4 Семейный режим

Общий бюджет на нескольких пользователей не входит в MVP.

### 9.5 Несколько счетов

В MVP не разделяем расходы по счетам: наличные, карта, кошелёк.

### 9.6 Платные тарифы

Монетизация не входит в MVP. Сначала нужно проверить полезность продукта.

### 9.7 Банковские интеграции

Подключение банковских SMS, API банков или выписок не входит в MVP.

## 11. Основные сущности проекта

### 11.1 User

Пользователь Telegram-бота.

Основные поля:

* `id`;
* `telegram_id`;
* `first_name`;
* `last_name`;
* `username`;
* `currency`;
* `timezone`;
* `language`;
* `created_at`;
* `updated_at`.

### 11.2 Category

Категория операции.

Категории бывают:

* системные;
* пользовательские.

Примеры:

* Еда;
* Транспорт;
* Подписки;
* Доход;
* Прочее.

### 11.3 Transaction

Финансовая операция.

Типы:

* `expense`;
* `income`.

Основные поля:

* сумма;
* валюта;
* категория;
* комментарий;
* дата операции;
* дата создания;
* дата удаления для soft delete.

### 11.4 CategoryRule

Пользовательское правило категоризации.

Пример:

```text
такси → Транспорт
chatgpt → Подписки
обед → Еда
```

Если пользователь исправил категорию, бот запоминает это как правило.

### 11.5 Reminder

Настройка напоминаний.

Пример:

```text
Каждый день в 20:00 отправить:
Не забудь записать расходы за сегодня.
```

### 11.6 Budget

Бюджет пользователя.

В MVP бюджет может отсутствовать. В версии 1.1 используется для лимитов.

Пример:

```text
Еда: 1000 TJS в месяц
Транспорт: 400 TJS в месяц
```

### 11.7 Debt

Долг.

Добавляется в версии 1.1.

Примеры:

```text
дал Али 100
Али вернул 50
занял у Фарруха 200
```

## 12. Высокоуровневая архитектура

Система работает по webhook-модели.

```text
User
  ↓
Telegram Bot
  ↓ webhook POST
Cloudflare Worker
  ↓
Hono Router
  ↓
Webhook Security
  ↓
Update Idempotency
  ↓
User Resolver
  ↓
State Manager
  ↓
Message Parser
  ↓
Business Services
  ↓
D1 Database / KV
  ↓
Telegram API response
```

### 12.1 Основные компоненты

#### Telegram Bot API

Используется для:

* получения сообщений через webhook;
* отправки ответов пользователю;
* отправки inline-кнопок;
* отправки файлов CSV;
* настройки команд бота.

#### Cloudflare Worker

Главный backend runtime.

Обрабатывает:

* Telegram webhook;
* health check;
* cron-задачи;
* будущий dashboard API.

#### Hono

Лёгкий web-framework для роутинга внутри Worker.

Примеры маршрутов:

```text
POST /telegram/webhook
GET /health
GET /api/reports/month
GET /api/export/csv
```

#### Cloudflare D1

SQL-база данных для постоянных данных:

* пользователи;
* категории;
* транзакции;
* правила категоризации;
* бюджеты;
* долги;
* напоминания.

#### Cloudflare KV

Используется для временных данных:

* состояние диалога;
* защита от повторной обработки `update_id`;
* rate limiting;
* временные callback-сессии.

#### Drizzle ORM

Используется для:

* описания схемы БД в TypeScript;
* типизированных запросов;
* миграций;
* уменьшения риска ошибок в SQL.

## 13. Основные принципы UX

### 13.1 Пользователь пишет как человек, не как программист

Бот должен понимать короткие сообщения:

```text
35 обед
120 продукты
+300 зарплата
вчера 50 кофе
```

Пользователь не обязан писать команды для каждой операции.

### 13.2 Бот не должен перегружать ответами

Ответ должен быть коротким:

```text
✅ Сохранено: 35 TJS · Еда
Остаток сегодня: 155 TJS
```

Если бот слишком много объясняет после каждой записи, пользователь перестанет им пользоваться.

### 13.3 Ошибка должна исправляться быстро

После записи бот может показать кнопку:

```text
[Отменить]
```

Для средней уверенности категории:

```text
Категория: Еда?
[Верно] [Изменить]
```

### 13.4 Команда `/cancel` должна работать всегда

Если пользователь находится в любом состоянии, `/cancel` сбрасывает его.

Пример:

```text
Действие отменено. Можешь продолжить обычной записью, например:
25 такси
```

### 13.5 Отчёты должны быть текстовыми и понятными

MVP не использует графики. Отчёты должны хорошо читаться прямо в Telegram.

## 14. Основные бизнес-правила

### 14.1 Каждая транзакция принадлежит одному пользователю

Все операции должны быть привязаны к `user_id`.

Запрещено получать транзакции без фильтра по `user_id`.

Правильно:

```typescript
await transactionRepository.findByUserId(user.id);
```

Неправильно:

```typescript
await transactionRepository.findAll();
```

### 14.2 Soft delete для транзакций

Удаление транзакции не должно физически удалять запись из базы.

Вместо этого заполняется поле:

```text
deleted_at
```

Активная запись:

```text
deleted_at = NULL
```

Удалённая запись:

```text
deleted_at = '2026-06-04T12:00:00.000Z'
```

Все запросы отчётов и истории обязаны учитывать только активные записи.

### 14.3 Идемпотентность Telegram update

Telegram может отправить один и тот же update повторно.

Чтобы не записать расход два раза:

1. получить `update_id`;
2. проверить его в KV;
3. если уже обработан — вернуть `200 OK`;
4. если новый — сохранить в KV с TTL;
5. обработать сообщение.

### 14.4 Категория может быть определена с разной уверенностью

Уровни уверенности:

| Confidence  | Поведение                                    |
| ----------- | -------------------------------------------- |
| `> 0.8`     | Сохранить сразу                              |
| `0.5 - 0.8` | Сохранить и предложить подтвердить категорию |
| `< 0.5`     | Не сохранять, спросить категорию             |

### 14.5 Пользовательское правило важнее системного словаря

Если системный словарь говорит:

```text
такси → Транспорт
```

но пользователь изменил правило на:

```text
такси → Работа
```

то для этого пользователя нужно применять категорию `Работа`.

### 14.6 Все состояния имеют TTL

Состояние диалога нельзя хранить бесконечно.

Пример:

```typescript
const STATE_TTL_SECONDS = 15 * 60;
```

Через 15 минут состояние должно исчезнуть.

## 15. Нефункциональные требования

### 15.1 Производительность

Целевые показатели:

| Операция                      | Цель         |
| ----------------------------- | ------------ |
| Ответ после записи транзакции | до 1 секунды |
| `/today`                      | до 500 мс    |
| `/week`                       | до 500 мс    |
| `/month`                      | до 1 секунды |
| CSV export за месяц           | до 2 секунд  |

### 15.2 Надёжность

Система должна:

* не создавать дубли транзакций;
* не терять данные после успешного сохранения;
* корректно обрабатывать повторные webhook-запросы;
* возвращать `200 OK` Telegram после обработки update;
* логировать технические ошибки без утечки финансовых данных.

### 15.3 Безопасность

Обязательные правила:

* Telegram bot token хранится только в Cloudflare Secrets;
* webhook endpoint проверяет secret token;
* данные пользователей изолированы через `user_id`;
* нельзя логировать содержимое финансовых сообщений;
* нельзя логировать токены и секреты;
* rate limiting защищает от флуда.

### 15.4 Масштабируемость

MVP должен быть рассчитан на небольшое количество пользователей, но архитектура не должна мешать росту.

Решения, которые помогают масштабированию:

* serverless backend;
* SQL-индексы по `user_id` и датам;
* KV для временных состояний;
* отдельные модули backend;
* типизированный доступ к базе;
* понятные boundaries между parser, services, repositories.

### 15.5 Поддерживаемость

Код должен быть организован по модулям:

```text
src/
  routes/
  modules/
    users/
    transactions/
    categories/
    parser/
    reports/
    reminders/
  db/
  telegram/
  shared/
```

Каждый модуль должен иметь понятную ответственность.

## 16. Риски и ограничения

### 16.1 Риск неправильной категоризации

Бот может ошибочно определить категорию.

Снижение риска:

* использовать confidence score;
* показывать кнопки подтверждения;
* сохранять пользовательские правила;
* иметь категорию `Прочее`.

### 16.2 Риск дублирования транзакций

Telegram может повторить webhook-запрос.

Снижение риска:

* сохранять `update_id` в KV;
* не обрабатывать уже известные update;
* проектировать обработчик как идемпотентный.

### 16.3 Риск превышения лимитов бесплатного тарифа

Если пользователей станет много, бесплатного тарифа может быть недостаточно.

Снижение риска:

* использовать индексы;
* не делать лишних запросов;
* кэшировать временные состояния в KV;
* контролировать количество cron-задач;
* перейти на платный тариф при росте.

### 16.4 Риск утечки финансовых данных в логах

Финансовые сообщения чувствительны.

Снижение риска:

* логировать только технические metadata;
* не логировать полный текст сообщений;
* маскировать суммы при необходимости;
* не писать секреты в console logs.

### 16.5 Риск слишком большого MVP

Если добавить бюджеты, dashboard, AI и долги сразу, первая версия станет слишком большой.

Снижение риска:

* MVP ограничивается базовым учётом;
* дополнительные функции идут в версии 1.1, 2.0 и 3.0;
* каждая версия имеет отдельные критерии готовности.

## 17. Критерии успешности MVP

MVP можно считать успешным, если выполнены следующие условия:

### 17.1 Пользовательские критерии

* пользователь может начать работу через `/start`;
* пользователь может записать расход за несколько секунд;
* пользователь понимает ответ бота;
* пользователь видит остаток дня после записи;
* пользователь может посмотреть отчёт за день, неделю и месяц;
* пользователь может удалить ошибочную последнюю запись;
* пользователь может экспортировать данные.

### 17.2 Технические критерии

* webhook работает стабильно;
* секрет webhook проверяется;
* повторный update не создаёт дубль;
* данные сохраняются в D1;
* временные состояния хранятся в KV;
* транзакции удаляются через soft delete;
* все запросы фильтруются по `user_id`;
* тесты парсера проходят;
* тесты отчётов проходят;
* деплой через Wrangler проходит без ошибок.

### 17.3 Продуктовые критерии

* пользователь возвращается к боту несколько дней подряд;
* пользователь записывает минимум 5–10 операций в неделю;
* отчёты дают понятную картину расходов;
* пользователь не нуждается в инструкции после первого онбординга;
* бот не требует ручной настройки перед первым использованием.

> 💡 Дополнено: критерии успешности разделены на пользовательские, технические и продуктовые, чтобы MVP можно было оценивать не только по факту реализации функций, но и по фактической полезности.
