## 2. Общее описание продукта

**Finance Telegram Bot** — Telegram-бот для личного финансового учёта.

Пользователь пишет боту обычные сообщения:

```text
35 обед
25 такси
+300 зарплата
вчера 50 кофе
```

Бот должен:

1. понять сообщение;
2. определить тип операции;
3. извлечь сумму;
4. определить дату;
5. определить категорию;
6. сохранить операцию;
7. показать короткое подтверждение;
8. показать остаток за день или актуальный финансовый контекст.

Пример ответа:

```text
✅ Расход сохранён

35 TJS · Еда · обед
Остаток сегодня: 155 TJS
```

Основная ценность продукта — быстрое добавление расходов и доходов без отдельного приложения.

## 3. Термины и роли

### 3.1 User

Пользователь Telegram-бота.

Идентифицируется через Telegram:

```typescript
telegram_id: string;
```

Внутри системы пользователь имеет собственный `user_id`.

Все финансовые данные должны быть привязаны к `user_id`.

---

### 3.2 Transaction

Финансовая операция.

Типы:

```typescript
type TransactionType = 'expense' | 'income';
```

Примеры:

```text
35 обед       → expense
+300 зарплата → income
```

---

### 3.3 Category

Категория операции.

Примеры:

* Еда;
* Транспорт;
* Дом;
* Связь;
* Подписки;
* Доход;
* Прочее.

Категории бывают:

* системные;
* пользовательские.

---

### 3.4 Parser

Модуль, который анализирует входящий текст пользователя.

Он должен определить:

* сумму;
* тип операции;
* дату;
* категорию;
* комментарий;
* confidence score.

---

### 3.5 Confidence score

Оценка уверенности парсера от `0` до `1`.

Правила:

| Confidence  | Поведение                                      |
| ----------- | ---------------------------------------------- |
| `> 0.8`     | Сохранить операцию сразу                       |
| `0.5 - 0.8` | Сохранить, но предложить подтвердить категорию |
| `< 0.5`     | Не сохранять, спросить категорию явно          |

---

### 3.6 UserState

Временное состояние диалога.

Примеры:

* пользователь выбирает валюту;
* пользователь подтверждает удаление;
* пользователь выбирает категорию;
* пользователь редактирует последнюю операцию.

Состояния хранятся в Cloudflare KV с TTL.

---

### 3.7 MVP

Минимальная первая версия продукта, которая уже полезна пользователю.

MVP должен покрывать:

* онбординг;
* запись расходов;
* запись доходов;
* автокатегоризацию;
* отчёты;
* историю;
* удаление последней операции;
* экспорт CSV;
* ежедневное напоминание;
* базовую безопасность.

## 4. Приоритеты требований

Для требований используется схема приоритетов:

| Приоритет | Значение                                   |
| --------- | ------------------------------------------ |
| Must      | Обязательно для версии                     |
| Should    | Желательно, но не блокирует тестовый релиз |
| Could     | Можно добавить при наличии времени         |
| Won't     | Не входит в эту версию                     |

## 5. Общие функциональные правила

### FR-GEN-001 — Все данные пользователя изолированы

**Приоритет:** Must
**Версия:** 1.0+

Все операции чтения и записи должны выполняться только в рамках конкретного `user_id`.

Нельзя получать транзакции, категории, бюджеты, долги или настройки без фильтрации по пользователю.

Правильно:

```typescript
await transactionRepository.findRecentByUserId(user.id, 10);
```

Неправильно:

```typescript
await transactionRepository.findRecent(10);
```

Acceptance criteria:

* пользователь A не видит данные пользователя B;
* все repository-методы принимают `userId`;
* тесты проверяют изоляцию данных;
* dashboard API в версии 2.0 также фильтруется по `userId`.

---

### FR-GEN-002 — Telegram message является главным интерфейсом MVP

**Приоритет:** Must
**Версия:** 1.0

В MVP все основные действия выполняются через Telegram:

* текстовые сообщения;
* команды;
* inline-кнопки;
* файлы, отправляемые ботом.

Web-dashboard не входит в MVP.

Acceptance criteria:

* пользователь может вести учёт без dashboard;
* все MVP-функции доступны из Telegram;
* бот не требует авторизации через браузер.

---

### FR-GEN-003 — Бот должен отвечать понятным текстом

**Приоритет:** Must
**Версия:** 1.0+

Все ответы должны быть:

* короткими;
* понятными;
* без технических ошибок;
* с примерами, если бот не понял пользователя.

Плохо:

```text
ParserError: amount_not_found
```

Правильно:

```text
Не понял сумму.

Попробуй так:
25 такси
100 продукты
+300 зарплата
```

---

### FR-GEN-004 — Команда `/cancel` должна работать всегда

**Приоритет:** Must
**Версия:** 1.0+

Если пользователь находится в любом временном состоянии, `/cancel` должен сбросить его.

Пример:

```text
Действие отменено. Можешь продолжить обычной записью:
25 такси
```

Acceptance criteria:

* `/cancel` удаляет состояние из KV;
* `/cancel` работает при выборе валюты;
* `/cancel` работает при подтверждении удаления;
* `/cancel` работает при выборе категории;
* после `/cancel` следующее сообщение обрабатывается как новое.

---

### FR-GEN-005 — Дублирующий Telegram update не должен создавать повторную запись

**Приоритет:** Must
**Версия:** 1.0+

Каждый Telegram update имеет `update_id`.

При получении update система должна:

1. проверить `update_id` в KV;
2. если update уже обработан — вернуть `200 OK`;
3. если update новый — сохранить marker в KV;
4. обработать сообщение.

Пример ключа:

```text
processed_update:{update_id}
```

TTL:

```text
24 hours
```

Acceptance criteria:

* один и тот же update не создаёт две транзакции;
* повторный webhook возвращает успешный HTTP-ответ;
* тест проверяет повторную отправку одного update.

## 6. Требования MVP / версия 1.0

### 6.1 Регистрация и онбординг

---

#### FR-MVP-001 — Команда `/start`

**Приоритет:** Must
**Актор:** User
**Точка входа:** Telegram command `/start`

При первом запуске бот должен:

1. создать пользователя, если его ещё нет;
2. сохранить Telegram metadata;
3. показать приветствие;
4. объяснить формат ввода;
5. предложить выбрать валюту;
6. установить язык `ru` по умолчанию;
7. установить timezone `Asia/Dushanbe` по умолчанию.

Пример приветствия:

```text
Привет. Я помогу быстро вести расходы прямо в Telegram.

Пиши расходы обычным текстом:
35 обед
120 продукты
+300 зарплата

Для начала выбери валюту.
```

Inline-кнопки:

```text
[TJS] [USD] [RUB] [Другая]
```

Acceptance criteria:

* новый пользователь создаётся в таблице `users`;
* повторный `/start` не создаёт дубликат пользователя;
* если пользователь уже существует, бот показывает короткое приветствие и подсказку;
* после `/start` пользователь может сразу отправить расход.

---

#### FR-MVP-002 — Выбор валюты

**Приоритет:** Must
**Версия:** 1.0

Пользователь должен выбрать основную валюту.

Поддерживаемые варианты MVP:

* `TJS`;
* `USD`;
* `RUB`;
* `EUR`;
* `UZS`;
* custom input.

По умолчанию:

```text
TJS
```

Поведение:

1. если пользователь нажал кнопку `TJS`, валюта сохраняется сразу;
2. если выбрал `Другая`, бот ждёт текстовый код валюты;
3. код валюты должен быть 3–5 символов;
4. код сохраняется в uppercase.

Пример:

```text
Валюта сохранена: TJS

Теперь можешь записать первый расход:
35 обед
```

Acceptance criteria:

* валюта сохраняется в `users.currency`;
* неправильный код валюты отклоняется;
* пользователь может изменить валюту позже через `/settings`.

> 💡 Дополнено: добавлены EUR, UZS и custom input, потому что продукт может использоваться не только в TJS/USD/RUB, а технически хранение валюты как строки это поддерживает.

---

#### FR-MVP-003 — Базовый онбординг

**Приоритет:** Must
**Версия:** 1.0

Онбординг должен быть коротким.

Обязательные шаги:

1. приветствие;
2. объяснение формата записи;
3. выбор валюты;
4. подтверждение настроек;
5. предложение записать первый расход.

Не нужно в MVP:

* длинная анкета;
* настройка всех категорий;
* установка бюджета;
* подключение банков;
* регистрация через email.

Acceptance criteria:

* онбординг занимает не более 2–3 сообщений;
* пользователь может пропустить сложные настройки;
* бот не блокирует запись расходов после первого запуска.

---

### 6.2 Запись расходов

---

#### FR-MVP-004 — Добавление расхода свободным текстом

**Приоритет:** Must
**Версия:** 1.0

Пользователь должен иметь возможность добавить расход обычным текстом.

Примеры:

```text
35 обед
25 такси
100 продукты
вчера 50 кофе
03.06 200 одежда
```

Бот должен определить:

* `amount`;
* `type = expense`;
* `category`;
* `note`;
* `transaction_date`.

Правило по умолчанию:

Если сообщение содержит сумму и не похоже на доход или долг, оно считается расходом.

Пример ответа:

```text
✅ Расход сохранён

35 TJS · Еда · обед
Остаток сегодня: 155 TJS
```

Acceptance criteria:

* расход сохраняется в `transactions`;
* сумма сохраняется как positive number;
* тип сохраняется как `expense`;
* дата по умолчанию — сегодня в timezone пользователя;
* note сохраняется без суммы и даты;
* после сохранения бот показывает остаток за день.

---

#### FR-MVP-005 — Поддержка разных форматов суммы

**Приоритет:** Must
**Версия:** 1.0

Парсер должен понимать суммы:

```text
35
35.5
35,5
1 200
1200
1,200
```

Нормализация:

```typescript
"35,5"  -> 35.5
"1 200" -> 1200
```

Правила:

* сумма должна быть больше `0`;
* отрицательные суммы не допускаются;
* для дохода знак `+` определяет тип, но в базе amount хранится положительным числом;
* максимальная сумма MVP: `1_000_000_000`.

Acceptance criteria:

* `35,5 кофе` сохраняется как `35.5`;
* `0 кофе` отклоняется;
* `-35 кофе` отклоняется;
* `+300 зарплата` сохраняется как income amount `300`.

> 💡 Дополнено: ограничение максимальной суммы нужно для защиты от ошибочного ввода и мусорных данных.

---

#### FR-MVP-006 — Остаток дня после каждой записи

**Приоритет:** Must
**Версия:** 1.0

После успешной записи расхода или дохода бот должен показывать остаток за текущий день.

Формула:

```text
daily_balance = today_income - today_expense
```

Пример:

```text
Остаток сегодня: 155 TJS
```

Если остаток отрицательный:

```text
Остаток сегодня: -45 TJS
```

Acceptance criteria:

* остаток считается только по активным транзакциям;
* soft-deleted транзакции не учитываются;
* используется timezone пользователя;
* после дохода остаток увеличивается;
* после расхода остаток уменьшается.

---

### 6.3 Запись доходов

---

#### FR-MVP-007 — Добавление дохода через знак `+`

**Приоритет:** Must
**Версия:** 1.0

Если сообщение начинается с `+`, бот должен считать его доходом.

Примеры:

```text
+300 зарплата
+1500 проект
+50 возврат
```

Ответ:

```text
✅ Доход сохранён

300 TJS · Доход · зарплата
Остаток сегодня: 455 TJS
```

Acceptance criteria:

* `+300 зарплата` сохраняется как `income`;
* знак `+` не сохраняется в note;
* amount сохраняется как `300`, а не `+300`.

---

#### FR-MVP-008 — Добавление дохода через ключевые слова

**Приоритет:** Should
**Версия:** 1.0

Бот должен распознавать доходы по словам:

```text
получил
заработал
зарплата
аванс
фриланс
проект
```

Примеры:

```text
получил 500
заработал 800 фриланс
зарплата 3000
```

Acceptance criteria:

* `получил 500` сохраняется как income;
* `зарплата 3000` сохраняется как income;
* если есть конфликт с расходом, приоритет отдаётся явному `+`.

### 6.4 Автокатегоризация

---

#### FR-MVP-009 — Системный словарь категорий

**Приоритет:** Must
**Версия:** 1.0

В MVP бот должен иметь системный словарь категорий.

Минимальные категории:

| Code            | Название    | Type    |
| --------------- | ----------- | ------- |
| `food`          | Еда         | expense |
| `transport`     | Транспорт   | expense |
| `home`          | Дом         | expense |
| `communication` | Связь       | expense |
| `entertainment` | Развлечения | expense |
| `health`        | Здоровье    | expense |
| `clothing`      | Одежда      | expense |
| `education`     | Образование | expense |
| `subscriptions` | Подписки    | expense |
| `income`        | Доход       | income  |
| `other`         | Прочее      | expense |

Пример словаря:

```typescript
export const CATEGORY_KEYWORDS: Record<string, string[]> = {
  transport: ['такси', 'маршрутка', 'автобус', 'бензин'],
  food: ['кофе', 'обед', 'ужин', 'завтрак', 'продукты', 'шаурма'],
  subscriptions: ['подписка', 'chatgpt', 'spotify', 'netflix'],
  income: ['зарплата', 'фриланс', 'проект', 'аванс'],
};
```

Acceptance criteria:

* `25 такси` определяется как `transport`;
* `35 обед` определяется как `food`;
* `200 chatgpt` определяется как `subscriptions`;
* неизвестная категория попадает в `other` или требует уточнения.

---

#### FR-MVP-010 — Пользовательские правила категоризации

**Приоритет:** Should
**Версия:** 1.0

Если пользователь исправил категорию, бот должен запомнить правило.

Пример:

1. Пользователь пишет:

```text
100 такси
```

2. Бот предлагает `Транспорт`.

3. Пользователь меняет на `Работа`.

4. Система сохраняет:

```text
keyword: такси
category: Работа
user_id: current user
```

При следующем сообщении:

```text
80 такси
```

Бот выбирает `Работа`.

Acceptance criteria:

* пользовательское правило имеет приоритет над системным словарём;
* правило применяется только для конкретного пользователя;
* правило не влияет на других пользователей.

---

#### FR-MVP-011 — Поведение при низкой уверенности категории

**Приоритет:** Must
**Версия:** 1.0

Если parser confidence ниже `0.5`, бот не должен сохранять транзакцию сразу.

Он должен спросить категорию:

```text
Я понял сумму: 75 TJS
Но не понял категорию.

Выбери категорию:
```

Inline-кнопки:

```text
[Еда] [Транспорт]
[Дом] [Связь]
[Прочее]
```

Acceptance criteria:

* транзакция не создаётся до выбора категории;
* временные данные сохраняются в KV;
* после выбора категории транзакция создаётся;
* если пользователь пишет `/cancel`, временные данные удаляются.

---

### 6.5 История и удаление

---

#### FR-MVP-012 — Команда `/history`

**Приоритет:** Must
**Версия:** 1.0

Команда `/history` показывает последние 10 активных операций пользователя.

Формат:

```text
🧾 Последние операции

1. 35 TJS · Еда · обед · сегодня
2. 25 TJS · Транспорт · такси · сегодня
3. +300 TJS · Доход · зарплата · вчера
```

Правила:

* показывать только `deleted_at IS NULL`;
* сортировка по `created_at DESC`;
* доходы показывать со знаком `+`;
* расходы без знака или со знаком `-` по выбранному UX-формату.

Acceptance criteria:

* если операций нет, бот показывает пустое состояние;
* удалённые операции не отображаются;
* максимум 10 операций.

---

#### FR-MVP-013 — Команда `/delete_last`

**Приоритет:** Must
**Версия:** 1.0

Команда `/delete_last` должна удалить последнюю активную операцию пользователя после подтверждения.

Шаг 1:

```text
Удалить последнюю запись?

35 TJS · Еда · обед
```

Inline-кнопки:

```text
[Да, удалить] [Отмена]
```

Шаг 2 после подтверждения:

```text
✅ Запись удалена
```

Техническое правило:

* физически запись не удаляется;
* заполняется `deleted_at`.

Acceptance criteria:

* удаляется только запись текущего пользователя;
* без подтверждения запись не удаляется;
* повторное нажатие на callback не должно ломать состояние;
* после удаления отчёты пересчитываются без этой операции.

---

#### FR-MVP-014 — Undo после сохранения

**Приоритет:** Could
**Версия:** 1.0

После сохранения операции бот может показывать кнопку:

```text
[Отменить]
```

Кнопка активна 30 секунд.

Поведение:

* если пользователь нажал кнопку в течение 30 секунд — операция soft-deleted;
* если позже — бот сообщает, что undo expired;
* команда `/delete_last` остаётся доступной всегда.

Acceptance criteria:

* undo удаляет только конкретную транзакцию;
* callback содержит `transaction_id`;
* нельзя удалить чужую транзакцию;
* истёкший undo не выполняется.

> 💡 Дополнено: undo был описан как UX-механизм. Здесь он помечен как Could для MVP, чтобы не блокировать первую версию.

### FR-1.1-004 — Учёт долгов

**Приоритет:** Must
**Версия:** 1.1

Бот должен понимать долговые сообщения.

```text
дал Али 100         → they_owe_me
Али вернул 50       → repayment
занял у Фарруха 200 → i_owe_them
вернул Фарруху 100  → repayment
```

Сущность:

```typescript
type DebtDirection = 'they_owe_me' | 'i_owe_them';

Acceptance criteria:

```

Acceptance criteria:

* советы основаны на данных пользователя;
* советы не должны быть агрессивными;
* не давать инвестиционные или юридические рекомендации.

## 10. Требования к парсеру сообщений

### FR-PARSER-001 — Parser pipeline

**Приоритет:** Must
**Версия:** 1.0+

Парсер должен работать по этапам:

```text
1. Normalize text
2. Detect command
3. Extract date
4. Extract amount
5. Detect transaction type
6. Extract note
7. Detect category
8. Calculate confidence
9. Return ParsedMessage
```

Пример типа:

```typescript
export interface ParsedMessage {
  rawText: string;
  normalizedText: string;
  type: 'expense' | 'income' | 'debt' | 'unknown';
  amount: number | null;
  note: string;
  categoryCode?: string;
  transactionDate: string;
  confidence: number;
  needsConfirmation: boolean;
}
```

Acceptance criteria:

* parser не пишет в базу;
* parser возвращает структурированный результат;
* business service решает, сохранять или уточнять.

---

### FR-PARSER-002 — Поддержка дат

**Приоритет:** Must
**Версия:** 1.0

Поддерживаемые форматы:

```text
без даты     → сегодня
вчера        → yesterday
позавчера    → today - 2 days
3 июня       → текущий год
03.06        → текущий год
2026-06-03   → ISO date
```

Acceptance criteria:

* дата сохраняется как ISO string;
* timezone пользователя учитывается;
* невалидная дата вызывает уточнение.

---

### FR-PARSER-003 — Конфликты парсинга

**Приоритет:** Must
**Версия:** 1.0

Если сообщение неоднозначное, бот должен уточнить.

Пример:

```text
Али 100
```

Это может быть:

* расход;
* долг;
* заметка.

Бот отвечает:

```text
Не понял тип записи.

Это расход или долг?
```

Inline-кнопки:

```text
[Расход] [Долг] [Отмена]
```

Acceptance criteria:

* неоднозначные сообщения не сохраняются молча;
* пользователь может выбрать тип;
* выбор сохраняется в state flow.

> 💡 Дополнено: добавлено явное поведение для конфликтов парсинга, потому что в overview есть уверенность парсера, но не все ambiguous cases были расписаны.

categories.user_id = NULL

## 13. Требования к состояниям диалога

### FR-STATE-001 — KV state с TTL

**Приоритет:** Must
**Версия:** 1.0+

Все временные состояния должны храниться в KV.

Ключ:

```text
state:{telegram_id}
```

TTL:

```text
15 minutes
```

Пример:

```typescript
interface UserState {
  action: 'awaiting_currency' | 'awaiting_category' | 'awaiting_confirm_delete';
  payload: Record<string, unknown>;
  expiresAt: number;
}
```

Acceptance criteria:

* состояние автоматически исчезает;
* после завершения действия состояние удаляется;
* `/cancel` удаляет состояние сразу.

---

### FR-STATE-002 — Новая команда сбрасывает старое состояние

**Приоритет:** Should
**Версия:** 1.0

Если пользователь был в состоянии выбора категории, но отправил `/today`, бот должен:

1. сбросить старое состояние;
2. выполнить `/today`.

Acceptance criteria:

* пользователь не застревает в старом сценарии;
* команды имеют приоритет над состояниями.

## 14. Требования к inline-кнопкам и callback actions

### FR-CALLBACK-001 — Callback data format

**Приоритет:** Must

---

### FR-CALLBACK-002 — Ответ на устаревший callback

**Приоритет:** Must
**Версия:** 1.0+

Если пользователь нажал старую кнопку, бот должен ответить понятно.

Пример:

```text
Это действие уже недоступно. Используй команду заново.
```

Acceptance criteria:

* бот не падает;
* данные не повреждаются;
* пользователь получает понятный ответ.

## 15. Требования к ошибкам и fallback-сценариям

### FR-ERR-001 — Не понял сообщение

**Приоритет:** Must
**Версия:** 1.0+

Если бот не понял сообщение:

```text
Не понял запись.

Попробуй так:
25 такси
100 продукты
+300 зарплата
```

Acceptance criteria:

* пользователь получает пример;
* ошибка не логируется как critical;
* сообщение не сохраняется как transaction.

---

### FR-ERR-002 — Ошибка сохранения

**Приоритет:** Must
**Версия:** 1.0+

Если база недоступна или запись не сохранилась:

```text
Не удалось сохранить запись. Попробуй ещё раз.
```

Acceptance criteria:

* пользователь не получает technical stack trace;
* ошибка логируется без финансового текста;
* повторная попытка не создаёт дубль, если первая запись всё же была сохранена.

---

### FR-ERR-003 — Rate limit

**Приоритет:** Must
**Версия:** 1.0+

Ограничение:

```text
30 сообщений / минуту / пользователь
```

При превышении:

```text
Слишком много сообщений. Подожди немного и попробуй снова.
```

Acceptance criteria:

* limit хранится в KV;
* TTL 60 секунд;
* команды безопасности не обходят limit;
* webhook всё равно возвращает корректный HTTP-ответ.

---

## 16. Требования к данным и изоляции пользователей

### FR-DATA-001 — Soft delete для transactions

**Приоритет:** Must
**Версия:** 1.0+

Удаление операции должно заполнять:

```text
deleted_at
```

Запросы отчётов, истории и экспорта должны использовать:

```sql
WHERE deleted_at IS NULL
```

Acceptance criteria:

* `/delete_last` не удаляет строку физически;
* `/history` не показывает удалённую запись;
* `/month` не учитывает удалённую запись.

---

### FR-DATA-002 — Audit-friendly timestamps

**Приоритет:** Should
**Версия:** 1.0+

Все основные записи должны иметь:

```text
created_at
updated_at
```

Acceptance criteria:

* timestamps создаются при insert;
* `updated_at` обновляется при edit;
* формат ISO string.

> 💡 Дополнено: timestamps нужны для отладки, истории операций и будущего dashboard.
